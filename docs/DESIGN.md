# braid design

braid runs a team of coding agents against one repository. A plan is a graph of tasks. Each task
runs in its own git worktree, and its output has to pass your checks before it is merged. The harness
never writes to your branches. Everything lands on `braid/<runId>/integration`, which you review
and merge yourself.

## Why not munder-difflin

We looked at [munder-difflin](https://github.com/chaitanyagiri/munder-difflin) (MIT, Electron,
about 88k lines). It has good ideas: a single process that commits, per-agent mailboxes, and hop caps
against agents replying to each other forever. Its core bet is different from ours:

| | munder-difflin | braid |
| --- | --- | --- |
| Agent control | Drives each CLI's interactive TUI through a PTY; hook bridges, keystroke injection and idle detection per CLI | Headless JSON modes (`claude -p --output-format stream-json`, `codex exec --json`); one parser per CLI |
| Orchestration | A "god" LLM agent routes work from a long system prompt | Deterministic scheduler in code; the LLM only plans and does task work |
| Done means | The agent says it is done | Verify commands pass on the task, an optional reviewer approves, and verify passes again after the merge |
| Isolation | Agents share working directories; auto mode passes `--dangerously-skip-permissions`-style flags | A git worktree per task, a tool allowlist, and no Bash by default |
| Cost | Reported | A token allowance per task and a time limit per agent call, on by default. A task that spends its allowance fails and the others carry on; an optional run-wide cap stops scheduling |
| Shape | Desktop app | CLI and library first; a UI reads the same event log |

We borrowed ideas, not code.

## Architecture

```
plan.json ─► Orchestrator (code, deterministic)
               │  DAG scheduling · concurrency · touches · token limits · retries
               ▼
         per task:  worktree from the last verified integration head
                    ├─ setup   (npm ci, ...)
                    ├─ worker  Driver.run(canEdit)        ── claude | codex | gemini | nim | mock
                    ├─ commit
                    ├─ verify  (task worktree)            ── fail ─► retry with output as feedback
                    ├─ review  Driver.run(read-only)      ── reject ─► retry with issues as feedback
                    └─ merge   (serialized)               ── conflict ─► pull latest into task branch,
                         │                                               resolver agent fixes markers only
                         └─ verify again on the combined tree ── fail ─► roll back, pull latest, fix on top
                            (verifyMerge, else the task's verify)
```

- `src/orchestrator.ts`: the scheduler, the task lifecycle, and serialized merges followed by verification.
- `src/drivers/*`: the `Driver` interface plus the Claude, Codex, Gemini and mock drivers, and one for OpenAI-compatible APIs (NVIDIA NIM). Gemini and NIM are not yet tested against a live install. Every CLI maps to one `AgentEvent` stream.
- `src/git.ts`: worktrees, commits, merges. It only ever writes to `braid/*` branches. The commands that can sit in a git hook take the run's abort signal (see Stopping and limits).
- `src/touches.ts`: whether two tasks' `touches` could match the same path, which decides whether they may run together (see Scheduling).
- `src/proc.ts`, `src/spawn.ts`, `src/sandbox.ts`: running commands and agents (process groups, stopping a whole tree, `.cmd` wrappers on Windows) and the container sandbox with its labels and stale sweep.
- `src/failures.ts`, `src/hints.ts`, `src/host.ts`: telling a provider's bad moment from the agent's failure, the one-line hint when a command needed a terminal, and the host and PID namespace a recorded pid is from.
- `src/clean.ts`, `src/pr.ts`: `braid clean` and `braid pr`.
- `src/branches.ts`: the read-only git views the dashboard shows (a run's task branches, and the history of the whole repo), plus a `git fetch` that only moves remote-tracking refs.
- `src/store.ts`: `.braid/runs/<id>/` holds `plan.json`, `state.json` (written atomically), `events.jsonl`, and `tasks/<id>/<role>-<n>.jsonl` with the full transcript of every agent turn.
- `src/watch.ts` + `ui/index.html`: a read-only dashboard with no dependencies. It listens on loopback only, rejects foreign `Host` headers, and polls the run files (fs.watch is unreliable on Windows). The mascot and agent sprites are original pixel art drawn in code, under MIT.
- `src/planner.ts`: a read-only agent that turns a goal into a checked plan. You edit the plan before running it.

## Invariants

1. The base branch and your working tree are never modified. `.braid/` goes into `.git/info/exclude`, not your `.gitignore`.
2. The integration branch only holds states that passed verification. A merge that breaks the combined tree is rolled back.
3. Merges are serialized, so only one process writes to the integration worktree at a time.
4. A dependent task starts from a tree that already contains its dependencies' merged work. A new task forks from `state.verifiedHead` (the last head that passed the combined check), never from the live integration HEAD: while another merge is being checked the HEAD already is that merge, and a task forked from it would carry the merge along even when the check rolls it back.
5. Every agent turn is logged in full, so a failure can be reproduced from the logs alone.
6. `state.json` says truthfully whether a run is going. A resume claims the file first (status `running`, this process's pid and host) before any slow setup, and puts the old file back if the resume fails to start. Without that, `braid clean` would read the previous end of the run as finished while its worktrees are being set up again. A short window remains between reading the old state and that first write.

## Security model

Headless agents cannot ask for permission, so any tool not on the allowlist is denied. The default is
`Read, Edit, Write, Glob, Grep`: no Bash, no network tools. Verify and setup commands come from the
plan (your team's own config) and run in a shell. A worktree is **not** a sandbox. An agent that is
allowed Bash can reach anything your user can. Only grant `Bash(...)` patterns you trust, and use the
container `sandbox` (`agent: true`) for untrusted work. Without a sandbox, verify and setup commands also run on the host, and they execute code the agents wrote.

Everything braid starts is given as separate arguments and not built into a shell string, except the plan's own `setup` and `verify` commands, which run in a shell. On Windows an agent CLI from npm, or a `gh` named by `BRAID_GH_BIN`, can be a `.cmd` or `.bat` wrapper, and Node can only start one through `cmd.exe`, which parses the command line a second time: it reads a `"` as the end of a quote, expands `%NAME%` and stops at a line break. None of those can be quoted safely, so `spawnable()` in `src/spawn.ts` refuses such an argument with an error, and free text (an agent prompt, the body of a pull request) goes on standard input. Not run on real Windows: the rules are unit-tested with a simulated platform.

## Team usage (now)

- Commit plans to the repo (for example `plans/*.json`) so the team shares task graphs and verify commands.
- Each person runs `braid` locally with their own CLI subscription.
- Agents are isolated from personal setup: the Claude driver passes `--setting-sources project,local --strict-mcp-config`, so personal plugins, hooks, output styles and MCP servers never leak into a run. Only the repo's own `.claude/` settings and `CLAUDE.md` apply, so the same plan behaves the same on every machine.
- The integration branch is an ordinary branch: push it and open a PR as usual, or let `braid pr` do both (see Pull requests, below).

## Roadmap

1. ~~**Cheaper conflict handling.**~~ Shipped. On a merge conflict braid merges the newer integration work into the task branch, and a narrow resolver agent removes the markers while keeping both sides' changes. The task is not redone. Nothing is committed while markers remain. A combined-tree verify failure is fixed on top of the existing work the same way. In the real smoke run the resolver cost $0.09, versus about $0.21 for a full redo.
2. ~~**Resume.**~~ Shipped as `braid resume [runId]`. Merged tasks stay done, every other task is retried with fresh attempts, and spend carries over so the budget covers the whole run. The integration branch is rewound to `verifiedHead` (the head after the last verified merge), which drops any half-done merge from a crash. A run whose process is still alive is refused. The resume claims `state.json` before any slow setup (invariant 6) and first removes the lock files that a git killed outright left on the run's own branches (event `stale_locks_removed`), which would otherwise fail every resume the same way.
3. ~~**Watch UI.**~~ Shipped as `braid watch`, `braid run --watch` and `braid demo`: a local read-only page (`ui/index.html`, `src/watch.ts`) that tails the run files over SSE.
4. ~~**Container sandbox.**~~ Shipped, opt-in: a `sandbox` section in the plan (or `braid run --sandbox IMAGE`), Docker or Podman (`src/sandbox.ts`). Setup and verify commands run in a throwaway container with only the task worktree mounted at `/work`, all capabilities dropped, no privilege escalation, your uid, and no network for verify (setup keeps it). With `agent: true` the agent CLI runs in the container too, which is what makes `Bash(...)` in `allowedTools` safe: it can only touch the worktree, not your other branches, your `.git` or your home directory. Secrets are passed by variable name (`env`), never by value. Checked against real Docker for setup and verify (isolation, no network, file ownership, an image with its own `ENTRYPOINT`); running the agent inside a container is covered only by a fake runtime, since it needs an image with the agent CLI installed (see `examples/sandbox/Dockerfile`). Containers are labelled, and the next sandboxed run sweeps the ones that a braid killed with SIGKILL left behind (see Stopping and limits); that sweep was checked only against a stand-in runtime. Not done: Windows path mapping, Podman rootless quirks, and a sweep from `braid clean`.
5. **Shared team server.** A daemon that queues runs, gives a shared dashboard, holds team memory (lessons learned per repo, fed back into worker prompts) and posts to Slack.

Workers run in `auto_edit` and reviewers in `plan`, so `allowedTools` and `maxTurns` do not apply, and spend is estimated from token counts and list prices. Gemini reports tokens only in its final event, so those of a call that is stopped before it are estimated from the streamed text (see Tokens and cost). NVIDIA NIM is in (`src/drivers/openai-compat.ts`, `driver: "nim"`, key in `NVIDIA_API_KEY`, endpoint override `BRAID_NIM_BASE_URL`): NIM is a hosted API with no agent program, so braid runs the tool loop itself against the OpenAI-compatible chat completions endpoint. The choice, the probes and the error handling were exercised against NVIDIA's real `/models` and error answers without a key and against a stand-in API with one; the preference list itself is a best guess from NVIDIA's documentation and has to be re-read when it ages. Dollars are not tracked for NIM unless prices are added to `BRAID_PRICES`; tokens always are. The same class serves any OpenAI-compatible endpoint (OpenRouter, Ollama, LM Studio), which is the remaining item along with OpenCode.
8. ~~**Replanning.**~~ Shipped, opt-in: `maxReplans` in the plan or `braid run --replan N`. When a task fails for good, a read-only planner agent looks at the failed attempt and the failure reasons, then either splits the task, rewrites it, or gives up. Code validates the proposal (new unique ids, deps only on merged tasks or each other, no cycles, at most 6 tasks); replacements inherit the failed task's driver, checks and limits (`touches`, `verifyMerge`, `reviewer` and `budgetTokens` too), and whatever waited on it now waits on the replacements. A task that failed because it used up its token allowance is not replanned (see Stopping and limits). The task ends as `replaced` and counts as complete. A bad proposal or a spent replan budget leaves it failed as before. While the planner thinks the task is `replanning`, so dependents are not blocked early. Replacement tasks that fail can be replanned again until `maxReplans` is used up.

## Tokens and cost

Every agent call reports tokens, and braid shows them in `braid run`, `braid status`,
`braid runs` and the dashboard (per task and per run). Tokens are what the CLI reported, split
into fresh input (cache writes included), cached input and output, except in the two cases below.
Dollars are not shown (see No cost in the interface), but `state.json` still records them: exact for
Claude, which reports them, and a list-price estimate for Codex and Gemini, where the run is flagged
`costEstimated`. If the tokens look wrong, that is the number to trust over the dollars. Claude's
cache-heavy usage means a trivial prompt can show tens of thousands of tokens, mostly cached.

Two figures are estimates, and the run carries no separate flag for them:

- **Gemini, a call that did not finish.** gemini-cli 0.53 reports token counts only in its final `result` event. A call that is stopped, killed or dead before it, or whose result is an error without figures, is estimated from what streamed, at about 4 characters per token: the prompt and tool output count as fresh input, assistant text and tool-call arguments as output. Each turn re-sends the whole conversation, mostly from cache, so only new content is counted once. The real figure is higher: reasoning tokens and the CLI's own system prompt and tool definitions never stream. What the CLI reported always wins over the estimate. A call that succeeds and reports nothing is left at 0 on purpose: that is what a renamed field looks like, and the weekly canary (see Testing) fails on it. The driver catches the abort and returns the usage so far (`ok: false`, text `aborted`), as the Claude and Codex drivers do.
- **NIM and other OpenAI-compatible endpoints, cached input.** Every turn re-sends the whole conversation. When the endpoint reports `cached_tokens` (zero included), that is trusted. When it does not, the first turn counts in full as fresh input, and after that fresh input is `max(0, prompt_n - (prompt_{n-1} + completion_{n-1}))` and the rest is cached. That is an approximation: an endpoint that does not cache bills the whole prompt, and the template overhead and the tool results of a turn are only roughly told apart.

## Cost estimates

Claude reports dollars. Codex and Gemini report only tokens, so `src/pricing.ts` turns tokens into an
estimated cost (fresh input, cached input and output priced separately) and `budgetUsd` use that figure. It is a list-price estimate: rates drift, an unknown model falls back to the driver's
default (`gemini-2.5-pro`, `gpt-5-codex`), and subscription plans are not billed per token at all.
Set `BRAID_PRICES` to a JSON file to correct or add prices:

```json
{ "gemini-2.5-pro": { "input": 1.25, "output": 10, "cachedInput": 0.125 } }
```

The Codex usage fields (`turn.completed.usage`) follow its docs and, like the driver, are untested against a live install.

## No cost in the interface

braid shows token counts and no dollar amounts anywhere: the dashboard, `braid run`/`status`/`runs`, the desktop notifications and the Settings window. Starting a run no longer asks for a spend cap, and the dashboard's start and resume flows have no cap field. What remains is internal: the agent drivers still record the cost their CLI reports (or an estimate from tokens, `pricing.ts`) in `state.json`, and a plan may optionally carry `budgetUsd`, in which case the scheduler stops starting tasks once it is reached. Nothing prompts for it. The guard rails that are always on are in tokens and minutes: see Stopping and limits.

## Scheduling and checks

- **Fork point.** A new task forks from `state.verifiedHead`, the last integration head that passed the combined check, never from the live HEAD (invariant 4). `test/fork-point.test.ts` covers the case where one task's merge is being checked, fails and is rolled back while another task starts.
- **`touches`.** A task may list the paths or globs it expects to change. `schedule()` starts a ready task only if no running task's `touches` could match a path that its own could (`touchesOverlap` in `src/touches.ts`). A task with no `touches` overlaps nothing: it is never held back and never holds another back. "Running" means in the scheduler's `running` map, so a task still in worktree setup (status `pending`) already owns its paths. With nothing running the answer is always "no overlap", so overlapping tasks take turns and the scheduler cannot stall on them.
  - **Matching.** Segment by segment on `/`, `**` crossing directories. `{a,b}` expands (more than 64 alternatives, or a pattern that is empty or has `..`, counts as the whole tree); a character class becomes `?` and any other group a `*`; case is ignored. It errs toward "overlap": a false positive only makes two tasks take turns, a false negative costs a merge conflict.
  - **Directories.** A trailing slash, or a last segment with no wildcard and no dot after its first character (or `*` alone), also covers everything under it. `Makefile` is taken for a directory too, which only costs an overlap. A bracket name such as `app/[id]`, `[...slug]` or `[[...path]]` is judged as written with each bracket group counted as one plain character, so it is a directory. A dotted directory name (`vendor/github.com`) is deliberately not recognised: tests rely on `docs/readme.md` not overlapping `**/*.ts`, so such a directory needs a trailing slash or `/**`.
  - **Why a task waits.** `TaskState.heldBy` lists the running tasks that hold back a ready task which has a free slot. It is cleared when the task starts, or when it only lacks a slot. The dashboard shows it as "Waiting for X: it changes the same files".
- **A held-back task is not a stall.** `schedule()` notes whether a pass left nothing running before it writes the snapshot. Tasks end during that write; if nothing is running afterwards and work is left, and the pass had not left it idle, it loops again instead of throwing `scheduler stalled`. A genuine stall still throws.
- **`verifyMerge`.** The check on the combined tree after a merge runs `task.verifyMerge`: the task's own, else the plan's, else the task's `verify`. An empty list skips the check. A failure rolls the merge back as before.
- **Reviewer.** `reviewer` on a task or the plan names the agent and model that reviews (`resolveReviewer` in `src/plan.ts`). Fields on the task win over the plan's, the task's own agent and model fill what is left out, and a model is only carried over to the agent it was meant for. The constructor looks up every task's and reviewer's driver before a run folder exists, so an unknown agent fails at once.
  - **No verdict.** A reviewer that failed without a boolean verdict ends the task with an error that names the reviewer and its model. The worker is not fed it as changes: redoing finished, verified work cannot fix a reviewer that is set up wrongly.
  - **Missing program.** A reviewer whose program cannot be started (`ENOENT`) throws `AgentUnavailableError` of kind `missing`, which halts that agent for the run like `quota`, so tasks that have not started are skipped. Other thrown errors (HTTP or auth failures from NIM) do not halt, since they can be transient. Not done: a probe of the reviewer's CLI at start-up (drivers have no availability API), so tasks already in flight still pay for one worker run.
  - **Halted reviewer.** `stopReason(driver, task)` also returns the halted state of a reviewed task's reviewer agent. It is read at the top of the attempt loop, after setup and in `canReplan`, and `schedule()` uses the same call. It does not abort a worker call that is already running (braid cannot), and no extra check sits before each call, since it would only skip a call that fails at once.
- **Replacements.** Tasks a replan adds inherit the failed task's `touches`, `verifyMerge`, `reviewer` and `budgetTokens` together with its driver and checks.

## Stopping and limits

- **Process trees.** Every child braid starts (setup and verify commands, agent CLIs, git, the sandbox probe) runs in its own process group (`taskkill /T` on Windows), registered in `live` in `src/proc.ts`, so a terminal Ctrl-C no longer reaches it by itself: `cli.ts` installs handlers for SIGINT, SIGTERM and SIGHUP, and `killAllChildren` runs when braid exits and on a force-quit. A group signal reaches only what stayed in the group. Codex starts every tool command as a session leader of its own, so stopping an agent is `stopTree` with `interrupt`: SIGINT first (Claude Code and Codex clean up their own commands and exit within milliseconds), SIGTERM after two seconds, SIGKILL after five, and descendants are snapshotted with `ps` before any signal so the escalation can still reach them once the agent is gone. Plain commands get SIGTERM then SIGKILL. Children that are still dying are kept in `dying`, so the exit hook finishes them instead of leaving them to an unref'd timer. Sandbox containers get a name (`braid-<hex>`) and are removed with `rm -f` (twice, since the first can land before the daemon registered the container) without waiting for the runtime to answer. A braid that is itself killed with SIGKILL cannot do any of this: see Containers, and Desktop sidecar for the app, which no longer kills its server. Verified on macOS only; the Windows path (`taskkill`, no groups) is reasoned from the docs.
- **Abort.** The run's `AbortSignal` reaches `shell()`, `exec()` (where used), the agent drivers and the git commands that can sit in a hook (next point). Everything that is stopped throws `AbortError` (`callAgent` and `verify` rethrow it), so every phase ends through the same catch in `runTask` and the task ends `skipped`. A Stop during the combined check after a merge undoes the merge (`merge_aborted`, not `merge_reverted`) so the integration branch still holds only verified states. A run whose tasks all merged is `done` even if the Stop arrived just after. `braid watch` stops the run it is driving and waits for it before exiting; a state file that says "running" for a process that is gone is shown as stopped.
- **Git and hooks.** `Git` takes the run's `AbortSignal`, and only the commands that run hooks use it: `commit`, `merge`, `mergeIn` (newer integration work merged into a task branch) and the task worktree's `worktree add`. A Stop kills git and the hook through the normal `stopTree` (SIGTERM, SIGKILL after 5 s) and throws `AbortError`, so `runTask` ends the task `skipped`; `braid resume` carries on.
  - **Settling.** `Git.settle` then aborts a merge left in progress, and removes `index.lock` and the lock on the branch checked out in the worktree, but only if the lock was made while the killed command ran and no git process names the worktree (read from `ps`; Windows and a minimal `ps` cannot say, so nothing is removed there). A killed `worktree add` removes its worktree, its admin directory and its branch. `settle` only works on worktrees the `Git` object created, never on the person's own checkout.
  - **Measured on macOS with Git 2.x.** Git removes its own `index.lock` on SIGTERM. Modern git does not hold `index.lock` during pre-commit or pre-merge-commit. A merge killed in pre-merge-commit leaves its result staged, with no `MERGE_HEAD` and no commit, which is why `serialMerge` resets the integration worktree to `verifiedHead` after an abort (event `merge_aborted`, also for a queued merge that never started because the signal was already aborted).
  - **Resume.** `Git.clearRunLocks(runId)` runs at the start of a resume and removes `*.lock` files under `refs/heads/braid/<run id>/` only (the id is validated and never used as a path), under the same guard, and logs `stale_locks_removed`. A git killed outright (SIGKILL, a second Ctrl-C) leaves such a lock, which fails with "cannot lock ref" on every resume of that task; removing the worktree does not clear it, because it lives with the repository. `ORIG_HEAD.lock` and `HEAD.lock` live in the worktree's own folder and go when the resume removes and recreates the worktree, which also discards any `MERGE_HEAD` a SIGKILL left.
  - **Not stoppable, by design.** Creating the run's own integration worktree (a new run, and the resume's attach): a Stop there is honoured as soon as git returns and the run ends as aborted with a branch to resume, because making it stoppable means restructuring `run()` so that a run without an integration branch can still be resumed. Also `add`, `status`, `reset`, `clean` and `diff`, which run no hooks. Git hooks have no time limit of their own: `timeoutMin` applies to agent calls only, and a hard limit would kill legitimately slow hooks, such as a full test suite.
  - **Edges.** A command that fails after the signal fired is taken as stopped even if it would have failed on its own: the run is ending either way, so the outcome is the same (the task is skipped), but a real hook rejection that races a Stop is reported as the Stop. The "no git process holds it" check reads `ps` for processes whose command line names the worktree or its git directory, as braid's own git always does; a process started elsewhere with only a working directory inside it is not seen, which is why the lock must also be newer than the killed command. On busybox `ps` braid cannot tell and keeps the lock, and a test that expects the lock gone would fail there. The error text of a failing stoppable command no longer includes the `--git-dir`/`--work-tree` pin arguments.
  - **Pinned git.** Host-side git never discovers a task worktree's repository from its `.git` pointer file, which a sandbox can rewrite to point at a directory whose config names a program to run: `Git` records each worktree's git directory when it creates it and passes `--git-dir`/`--work-tree` from then on. A worktree a killed `git worktree add` left locked is unlocked before it is removed.
- **Provider failures.** `src/failures.ts` tells a rate limit, overload or network error (`transient`) and running out of usage or credit (`quota`) apart from the agent's own failure. It judges only `AgentResult.error`, which each driver fills with what the provider or the CLI itself said (Claude's failed result text, Codex's `error`/`turn.failed` messages, Gemini's error events and stderr, NIM's request errors), never the agent's prose in `text`: Codex and Gemini put the agent's last words into `text` on failure, and "overloaded" or "service unavailable" is ordinary prose in many tasks. The wordings were taken from Claude Code 2.1.283 and Codex 0.147 run against stand-in APIs, from the Claude Code bundle (subscription notices, not executed) and from provider docs; the CLIs change their wording, so a miss falls back to the old behaviour (the attempt is spent). `callAgent` retries a transient failure after 20, 40, 80 and 160 seconds without counting an attempt or feeding anything back, and stops retrying when a limit is reached meanwhile; when that runs out, or at once for `quota`, it throws `AgentUnavailableError` (tagged with the role). After each pause it asks `stopReason` again for the agent the call goes to: a run-wide token limit reached, or that agent's quota gone, while it slept throws `CallStoppedError` carrying the real reason (not the old 529 text), and the task fails with it. A worker or resolver that never got an answer gives its attempt back in both cases; a reviewer or planner does not (the work had used its attempts), the planner failing keeps the task's real error and does not spend the replan. Quota halts only the agent that ran out (`halted` is per driver). `AgentUnavailableError` has a third kind, `missing`, for a reviewer's program that cannot be started: see Scheduling and checks.
- **Limits.** `timeoutMin` (default 30, capped at what a timer can hold) stops one agent call; the attempt then fails like any other and is retried on top of the partial work, except for a reviewer, whose timeout fails the task instead of sending the worker back. Planner agents (`braid plan`, the dashboard draft) have the same 30-minute limit. Tokens are limited per task, and optionally per run:
  - **Per task.** `plan.taskBudgetTokens` (default 3M, 0 = off), overridden by `TaskSpec.budgetTokens`, becomes `ResolvedTask.budgetTokens`. It is fresh input plus output summed over the task's worker, resolver, reviewer and replanner calls, cached input excluded. It is checked at the top of each attempt, after setup, before a replan and between `callAgent` retries, so one call can still overshoot it, and a worker that finishes while pushing the task over is still verified, reviewed and merged. The per-call time limit is what bounds a single call. A transient provider error that finds the allowance spent throws `TaskBudgetError`, not `agent unavailable`.
  - **What happens.** The task fails with `token budget exhausted for this task`, the other tasks carry on, and its dependents are blocked. Replacement tasks from a replan inherit the failed task's `budgetTokens` and get a fresh allowance of their own. A resumed task is measured against a per-task baseline (`TaskState.tokens` as restored), like `tokenBaseline` for the run.
  - **No replan.** A task that hit its allowance is not replanned (`canReplan` includes the per-task check), because the replanner call would be one more call charged to the exhausted task. A `TaskBudgetError` raised in the retry path of a replanner call is swallowed by `replan()` and leaves the task failed with its real error. Replanning such a task, with fresh allowances for the replacements, could be a deliberate follow-up.
  - **Whole run.** `plan.budgetTokens` is now only an optional run-wide cap with no default. When set, `limitReached()` checks it with `budgetUsd` (between calls, attempts and retries) and scheduling stops; the message is unchanged. It counts from the start of this process (`tokenBaseline`), so a resumed run gets a fresh allowance. `0` removes this cap only. Making `budgetTokens: 0` also switch off the per-task allowance was rejected: it would couple two knobs, contradict the type's own comment, and let `--budget-tokens 0` quietly disable the guard against a runaway task. Before this change `budgetTokens` defaulted to 3M per task in the plan as one pool for the run, so a plan that relied on that default now has the per-task allowance instead, and a run with many tasks can legitimately use more than 3M in all.
  - **A killed call.** It records the usage its agent had streamed (Claude per assistant message, Codex per finished turn, NIM per finished request, Gemini estimated: see Tokens and cost), so the limits see most of what a timeout cost but not all of it.
  - **Dashboard banner.** `runOutcome` in `ui/index.html` tells a per-task stop (kind `limit`, "task hit its limit": failed tasks, run otherwise fine) from the run-wide stop. It matches the error text `token budget exhausted for this task` (and the older `budget exhausted`), so that wording must not change without the page; `test/ui.test.ts` fails when it does. After a Stop the per-task banner says the run was then stopped, instead of saying that the others carried on.
- **Containers: labels and the sweep.** `--rm` and `rm -f` by name only run while braid is alive, so a braid that was SIGKILLed or crashed leaked its containers. Every container now carries `braid=1`, `braid.pid=<pid>` and `braid.host=<host>`, where the host is `hostIdentity()` in `src/host.ts`: the host name plus, on Linux, the PID namespace. `Sandbox.create` calls `sweepStale` once the runtime answers `info`. It lists `ps -a --filter label=braid` and runs `rm -f` on the containers whose host equals ours and whose pid is gone. It is best effort and never throws, so housekeeping cannot stop a run; it is limited to the runtime it was handed.
  - **What it leaves alone.** Its own pid and any live one (a pid that another process has since reused is conservatively left alone), a container from another host or namespace, one with no host label, and a row it cannot read. The host is there because a container daemon can be shared (a remote `DOCKER_HOST`, Docker Desktop under Windows and WSL, a dev container with the socket mounted), where the labelled pid does not exist here or is someone else's process. A host name that changed makes older leftovers look foreign and be left alone: the safe way to be wrong. Containers from before the labels are not swept, since nothing marks them as braid's.
  - **Where it shows.** The run log gets a `sandbox_sweep` event with the count, and the CLI prints a line. The dashboard's feed has no line for it yet and ignores it. `braid clean` does not sweep containers.
  - **Same rule for runs.** `state.json` records `host` as well. `braid clean` treats a run marked running on another host as live. `braid resume` and `braid pr` act on a run the person named and keep the pid-only check: refusing to resume a foreign crashed run would leave no way to override.
  - **Checked.** Against a stand-in runtime. The `docker ps --format` template was checked to be accepted by a real Docker with nothing to list; the sweep never removed a real container, and Podman's `{{.Label "key"}}` support is unverified (Podman was not installed).
- **Desktop sidecar.** The app starts `braid watch --control` with `BRAID_EXIT_ON_STDIN_CLOSE=1` and stops it by writing `quit` and a newline to its standard input. A closed input counts too, which covers an app that is killed or crashes, since the OS closes the pipe. Both map to the handler of the first SIGINT (`process.emit('SIGINT')`, which relies on that handler ignoring its arguments), exactly once: a later end of input is not read as a second Ctrl-C. Windows and POSIX use the same pipe.
  - **Without the variable** standard input is not read, because a terminal's belongs to the user. A launcher that sets it must keep the input open: a closed one, or `/dev/null`, makes `watch` begin to stop at once.
  - **What stopping does.** `stopActiveRun(15_000)` in `src/cli.ts` stops the run, waits up to 15 s for it to save, then exits. Agents usually stop at once; one that ignores SIGINT takes 2 s, one that ignores SIGTERM 5 s.
  - **The app side.** `sidecar.rs` asks first and kills only after `GRACE`, which is 20 s: it must outlast the sidecar's own 15 s, because a kill that lands earlier cuts the run off before it is saved. `test/desktop-grace.test.ts` reads both numbers out of the sources and requires `GRACE >= budget + 3 s`. If a stop does take longer than the grace, the kill leaks whatever the sidecar had not yet stopped.
  - **When.** Closing a window or switching repository stops the old server on a background thread. Quitting the app waits for all sidecars, up to the grace, so it can take a few seconds to exit while a run winds down. The demo server and a server that never came up are killed at once: the demo does not read stdin and has no run worth saving.
  - **Checked.** The Node side, against the compiled CLI with a run in flight (`test/containers-sidecar-stdin.test.ts`; the test's plan uses `exec node` so that node leads its process group under dash as well as bash), and the Rust stop logic with stand-ins. Not seen: the Tauri `CommandChild::write` reaching the real sidecar, and the app quitting with a run active.
- **No terminal, and the hint.** `terminalHint(output)` in `src/hints.ts` is a pure function over a small table of patterns (git credentials, ssh, sudo, gpg, and the "Device not configured" macOS prints when something opens `/dev/tty`). `runSetup` and `verify` use `failureTail()` to append at most one `Hint: braid runs this command without a terminal. ...` line to the output of a failing command. The match is on all of the output, and the output is cut to 3000 characters first so that the hint stays inside the 4000-character cut that stored task errors get. It explains; it never decides whether the command failed.
- **Draft cancel.** `POST /api/plan-draft` aborts the planner agent when the response closes before it was finished (page closed or reloaded, fetch aborted), so a planner that nobody waits for does not run to its 30-minute limit. It listens on `res` `close`: on Node 22 `req` `close` fires once the body is read, so it cannot detect a disconnect. The dashboard has no cancel button and does not abort its own fetch.

## Cleaning up

`braid clean` (`src/clean.ts`) removes what finished runs leave behind: kept task worktrees and task branches, and on request integration branches and run folders.

- **When a run is over.** `judgeRun`: status `done`, `failed` or `aborted`, or `running` with a pid that is not alive. EPERM counts as alive, and so does a pid recorded on another host or namespace (it cannot be looked up here). Runs without a readable `state.json` are skipped, because a run that is starting looks the same. Worktrees without a run folder are leftovers from a deleted run (a run makes its folder before its first worktree). Each run is re-read right before its own cleanup. `--older` counts from `endedAt`, or for a run that crashed from its last save.
- **Why a resume claims the file first.** Setup can take minutes, and until the resume writes its pid, `state.json` holds the previous end of the run, which `clean` would read as finished (invariant 6). A short window between reading the old state and that write remains.
- **"Merged elsewhere" for `--integration`.** A branch that holds the integration tip and is not under `braid/`, local or remote-tracking (`origin/main`). braid branches are excluded because a leftover task branch forked from the integration tip contains it, and the same command deletes it. Remote-tracking refs are only as current as the last fetch, and a squash or rebase merge does not make the branch count as merged, so that needs `--force`. A run that is not `done` keeps its integration branch unless `--runs` or `--force` is given: a tip that merely equals its base (nothing merged yet) would read as merged into main, and deleting it would leave a run that `braid resume` still picks and then fails on.
- **Safety choices.** Worktrees go before branches, because git will not delete a checked-out branch. A symlink under `.braid/worktrees/<run>` is unlinked and never passed to git, which would remove the worktree the link points at; a worktrees folder that is itself a link is `lstat`ed, unlinked and never read through. A branch checked out outside the run's folder (your own worktree) is kept. `state.json`'s `integrationBranch` must equal `braid/<id>/integration`, or it is left alone. The run folder is kept if anything of that run ended kept or failed, so `braid pr`, `braid resume` and the next clean still find it; a `git branch -D` that errors counts as failed (exit 1). Plain `--runs` without `--integration` deletes the folder.
- **Not done.** A container sweep (that runs only at the start of a sandboxed run). Reporting uncommitted work in a failed task's worktree before it is deleted: running git inside a worktree is unsafe (see Pinned git), so the note counts the task branch's commits that are not in the integration branch instead, and uncommitted files are lost silently. Cleaning a run folder that has no `state.json` (a crash before the first save): it cannot be told from a run that is starting, so `clean` says why it skipped it and a manual `git worktree remove` is needed. A pid that the OS has reused looks alive, so that run is skipped: the safe direction. The dry run is a prediction; it cannot know about other git refusals or locked files on Windows. Windows: the clean tests are written to run there but were not run, and the symlink test is skipped.

## Pull requests

`braid pr` (`src/pr.ts`) pushes a run's integration branch and opens a pull request with `gh`.

- **Arguments, not strings.** Everything goes to git and gh as argv. The pushed branch must be exactly `braid/<id>/integration`; `state.json` cannot make it push another. The base is validated with `git check-ref-format` and must not start with a dash, and a base of `HEAD` (a run started from a detached HEAD) needs `--base`. The remote must be a configured name. The push runs with `GIT_TERMINAL_PROMPT=0` and gh with `GH_PROMPT_DISABLED=1`, because they run without a terminal. It never pushes any other branch, never forces, and pushes nothing without gh.
- **Which run.** The newest with an integration branch, or the one named. One whose process is alive is refused; one marked running with a dead pid is treated as aborted. Only `done` runs, unless `--allow-partial`. As with `resume`, the check is on the pid alone.
- **The body.** `renderPrBody` is pure: it reads `state.json` and `plan.json`. The body is capped near 30k characters (GitHub stops at 65k). It goes to `gh` on standard input (`--body-file -`) so that it never meets `cmd.exe` on Windows; the title stays an argument (one line, at most 72 characters), and a title that a `.cmd` wrapper cannot take is refused with an explanation.
- **What it prints.** Free text cannot be quoted for every shell (PowerShell, cmd and POSIX sh differ), so the dry run and the no-gh output show the title and body as text, with a summary line for gh. The way to finish after a failure is to run `braid pr <id>` again with the same flags (the push is then a no-op). `shellQuote` is POSIX and used only for plain words: the `git push` line, `--base`, `--remote`. For a GitHub remote the no-gh output has a compare link (`githubCompareUrl`: https, ssh and scp-style URLs).
- **Not done.** Picking the repository for `--remote <other>`: gh resolves the base repository itself, so `--remote` only controls where the branch is pushed, and with several remotes the two can differ (`gh repo set-default`). Passing `--repo`, including GitHub Enterprise host forms, would change the argv shape. `git push` inherits the user's config, so `push.followTags` could push annotated tags along with the branch; the branch itself is always the explicit refspec. Windows: the gh-driven tests use a shebang stand-in and are skipped there; the pure tests were not run there.

## Testing

- **Unit and end to end.** `npm test` builds and runs `node --test` over `dist/test`. The scheduler tests use the mock driver; tests of agent output use stand-in programs (shebang scripts, so they skip on Windows). Real git runs in temporary repositories.
- **The dashboard script.** `test/ui.test.ts` syntax-checks every inline script in `ui/index.html` and runs the page's function declarations in a `vm` with a stub page, against run states written by the real orchestrator. It asserts on an outcome's kind and key words, not exact copy, so wording can change but not the kinds, or what the page looks for in the orchestrator's error text (`token budget exhausted`, `agent unavailable: usage or credit limit reached`). It also compares the page's token formatting with `describeTokens` in `src/tokens.ts`, so changing only one side fails. It relies on the page keeping its code in an IIFE of plain function declarations and arrow-function consts; a script of type `module` would not be syntax-checked, and a function that needs a global the stub lacks (`document`, `location`) needs the stub extended.
- **The canary.** `scripts/canary.mjs` is the only check against real agent output formats. For each usable agent it builds a tiny repository, runs a two-task plan through the built braid and asserts that the run is done, both tasks merged, both files are on the integration branch, and tokens and a final summary were read. The last two are what a renamed field in a CLI's output silently breaks without failing the run. `test/canary.test.ts` checks the script itself with stand-in agents that can simulate drift (`CANARY_FAKE_DRIFT`, such as `claude:usage` or `gemini:result`).
  - **Workflow.** `.github/workflows/canary.yml` runs weekly and by hand with the repository secrets `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` (also given to Codex as `CODEX_API_KEY`), `GEMINI_API_KEY` and `NVIDIA_API_KEY`, and the optional variables `CANARY_MODEL_CLAUDE`, `CANARY_MODEL_CODEX`, `CANARY_MODEL_GEMINI` and `CANARY_MODEL_NIM`. An agent without a secret is skipped. With `--require-keys` the script exits 1 when no agent passed, and the workflow adds `--strict` when the `drivers` input is given, so an agent asked for by name that could not run fails the job.
  - **Never run against real agents.** Untested assumptions: that the current CLI flags and sign-in work in CI, that Codex reads its key from `CODEX_API_KEY` or `OPENAI_API_KEY`, and that a real model completes the trivial task. Run it once from the Actions tab after merging, and expect the first run to fail for such reasons rather than for drift. The `--fake` path on Windows (`.cmd` stand-ins) is untested; its test is skipped there.
- **CI.** `ci.yml` runs `npm test`, the binary build and `scripts/smoke.mjs` on Linux, Windows and macOS, and the desktop app's Rust tests on macOS (`desktop-rust`). That job needs no extra libraries on macOS and runs on every push and pull request, because one job in a workflow cannot have its own path filter without a third-party action or a fragile diff step; `rust-cache` keeps it cheap once warm. `tauri-build` needs the sidecar file `desktop/src-tauri/binaries/braid-<rust host triple>` to exist, even empty. `desktop-windows.yml` builds and installs the Windows app and runs the Rust tests after it. Not done: Rust tests on Linux, which needs the WebKitGTK system packages to compile Tauri.
- **Not run.** Windows for the new git, lock, `braid clean`, `braid pr`, canary and sidecar work; the sweep against a real container; Podman; the real Tauri app quitting with a run active; the canary against real agents. See Verified where in the README.
